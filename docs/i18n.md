# 多語系與 Editor 設定入口實作計畫

> 狀態：已實作，2026-09-07。本文同時保留介面契約與驗收基準。

## 1. 目標與驗收範圍

第一版支援 `zh-TW`（繁體中文）與 `en`（英文），並把 Editor 右上角最後兩個固定
入口整理為：

```text
[金鑰 icon] [設定 icon]
```

設定 icon 打開一個貼近按鈕、外觀與既有右鍵選單一致的選單，內含：

- **歷史紀錄**：關閉選單後開啟既有 `HistoryPanel`；功能、資料與版面不另做一套。
- **語言**：關閉選單後開啟語言 modal，列出「中文（繁體）」與「English」。

使用者點選語言後立即保存偏好並重新載入目前頁面。選到目前語言時只關閉 modal，
不做無意義的重載。語言是瀏覽器層級偏好，不屬於專案；切換專案、回到專案列表或
重新啟動後仍沿用。沒有偏好或偏好值損壞時固定使用 `zh-TW`，不依瀏覽器語言自動
改變既有使用者看到的預設。

英文模式涵蓋：專案列表、Editor、所有第一方 modal／選單／提示／無障礙標籤、
Blockly 自帶介面、內建積木與官方隨附積木包、官方 panel，以及第一方 API、驗證與
執行錯誤。使用者輸入、專案名稱、流程 log、外部服務內容及第三方積木／插件自行
提供的文字保持原文；第三方沒有英文翻譯時使用它宣告的原文語言（§3 的
`defaultLocale`）。

## 2. 前端語系基礎

新增單一 i18n 模組作為所有第一方顯示文字的入口：

- 定義 `Locale = 'zh-TW' | 'en'`、支援語系列表、原生語言名稱，以及型別化的
  `t(key, params?)`。繁中 catalog 是完整基準，英文 catalog 必須具備相同 key；
  開發／測試時缺 key 直接失敗，正式環境才回退繁中。
- catalog 值可為字串或帶參數的 formatter，數字、日期、相對時間與複數使用目前
  locale 的 `Intl`，不再在元件內寫死 `toLocaleString('zh-TW')` 或拼接中英文句子。
- **catalog 是 TypeScript 模組，不是 `.json` 也不是 `.po`。** 上面那兩條要求
  ——缺 key 直接失敗、值可以是帶參數的 formatter——都需要型別；`.json` 給不了
  型別化的 `t(key, params)`，`.po` 則要求用原文當 msgid，正好違反 §3「不用中文
  原文當 key」那條線。TS catalog 就是翻譯檔，只是編譯得過。要抽成資料檔的時機
  是翻譯交給非工程師或 TMS 處理的那一天，兩種語言、同一個作者還沒到那裡。
- 在 React 掛載前從既有 `prefs.ts` 讀取 `blockyard.pref.locale`，同步設定
  `document.documentElement.lang` 與頁面標題。因為切換會重載，元件不需要維護
  第二份可熱切換狀態；React 元件與非 React helper 都讀同一個已初始化 locale。
- 將 `packages/editor/src` 中所有使用者可見的第一方硬編碼文字移入 catalog，包含
  `aria-label`、`title`、toast、空狀態、錯誤前綴、確認文案與匯入／擴充功能流程。
  原始碼註解、測試名稱與開發者 `console` 訊息不需翻譯。
- `registerManifests` 接收目前 locale，繁中使用 `blockly/msg/zh-hant`、英文使用
  `blockly/msg/en`。語言改變採整頁重載，避免在已有工作區上替換 Blockly 全域訊息
  或重定義積木而留下半套語言。

## 3. 積木包的翻譯

### 3.1 翻譯是獨立檔案，不進 manifest

`manifest.yaml` 是**契約**——積木長什麼樣、參數是什麼型別、回傳什麼型別，
`check_coverage()` 與 `diff()` 都是對著它算的。翻譯是**呈現**：它換掉使用者
看到的字，但不改變任何一顆積木的形狀。兩者不該住在同一個檔案裡。

所以翻譯放在包目錄的 `locales/<locale>.yaml`：

```text
mypack/
  manifest.yaml        # 原文，翻譯不會動到它
  main.py
  locales/
    en.yaml
    ja.yaml
```

這個決定買到四件事：

- `_bundled/*/manifest.yaml` 現在有一半的價值在那些說明為什麼這樣宣告的註解。
  把五種語言的巢狀翻譯塞進去，那份可讀的宣告就沒了。
- 第三方補一個語言不必改契約檔，PR 的差集只有一個新檔案；審閱畫面也不必決定
  要不要攤開那一大塊。
- 翻譯是積木包裡**唯一一種可以交給不是作者的人做**的貢獻。獨立檔才能讓它變成
  「丟一份 `locales/ja.yaml` 進來」。
- **不需要改 `install.py`。** `pack_files()` 是排除法（`PACK_SKIP_DIRS`），
  包目錄下的檔案預設就屬於這個包，`locales/` 跟 `ui/`、`tests/` 走同一條路。

### 3.2 原文語言要宣告得出來

manifest 新增選填 `defaultLocale`，**預設 `zh-TW`**，既有 v1 manifest 完全相容：

```yaml
manifestVersion: 1
id: data
name: 資料
defaultLocale: zh-TW
description: 儲存與讀取資料
```

沒有這個欄位的話，模型隱含「原文一定是繁中」。一個英文母語作者寫 `name: Data`，
中文使用者看到英文——**那跟中文包在英文介面顯示中文是同一件事**，但只有一邊
有名字。有了它，回退鏈才說得完整：requested locale → `defaultLocale` → 原文。

### 3.3 翻譯檔的形狀

翻譯以穩定 id 對應，不使用陣列位置或中文原文當 key：

```yaml
# mypack/locales/en.yaml
name: Data
description: Store and read data
blocks:
  set:
    text: "set %(name) to %(value)"
    args:
      name: { label: Variable name, help: Name to store }
    repeatLabel: "and %(value)"
buttons:
  docs: { label: Open documentation }
sections:
  lists: { title: Lists }
config:
  api_key: { label: API key, help: Create one in the provider console }
panels:
  chart: { name: Chart }
```

具名 section 新增可選 `id`，只有需要翻譯標題的 section 必須提供，純
`section: true` 不需 id。靜態 dropdown option 的翻譯以其穩定 `value` 為 key；
動態 dropdown 的 label 是外部／積木包資料，維持來源語言。

### 3.4 翻譯壞掉不擋整包

驗證的內容不變：翻譯引用的 config key、panel id、opcode、button id、section id、
arg name 與 option value 必須存在；每個翻譯版 `text`／`repeatLabel` 的 placeholder
集合必須和原宣告一致，否則換語言後積木會少一個孔。

**但失效的方式分兩種：**

| 場合 | 行為 |
|---|---|
| 執行期載入（`discover`、安裝） | 忽略**這一個語言檔**，記一筆警告，其餘照常 |
| `blockyard i18n check`、CI | 硬失敗 |

理由：翻譯不是契約。一個作者順手加了英文、打錯一個孔，壞掉的後果只是那個包的
字退回原文——執行語意一個字都沒變。若照契約欄位的規格在載入期拒絕整包，後果
會是他的包在**所有**使用者那裡都裝不起來，包含從來不看英文的那些人。
「manifest 驗得越嚴，`main.py` 的防呆越少」講的是宣告與實作之間的漂移，
不適用於一層純呈現的覆蓋。

未知 locale 可以保存並送到前端，第一版 UI 只暴露 `zh-TW` 與 `en`。

### 3.5 作者不想寫多語，答案是一個指令

把 `locales/` 設成選填只回答了一半——真正讓人不想寫的是那份巢狀 key 要自己猜。
新增 CLI 子命令（目前 `cli.py` 只有 `serve`）：

```bash
blockyard i18n extract mypack --locale en   # 產出／更新 locales/en.yaml
blockyard i18n check mypack                 # 硬失敗版的驗證（§3.4）
```

`extract` 產出的檔案所有 key 都已就位、值先填原文，作者只覆蓋想翻的那幾行；
重跑時保留既有翻譯，只補新增的 key 並標出原文已改動的項目。作者永遠不需要知道
key 長什麼樣，也不會打錯 id。這跟 `check_coverage()` 是同一個做法：**讓工具去
維持兩份東西對得起來，而不是靠人記得。**

### 3.6 前端消費與官方包

前端新增純函式 `localizeManifest(manifest, locales, locale)`，在 Blockly 註冊、
工具箱分組、金鑰資訊與擴充卡片使用前產生不可變的 localized view；找不到 requested
locale、某個區段或某個欄位時逐欄回退（§3.2 的回退鏈）。原始 manifest 仍用於版本
／變更比較，避免只因顯示語言不同就誤判積木包被更新。

為所有 `interpreter/builtins/*.yaml` 與官方 `_bundled/*/` 補上 `locales/en.yaml`，
包含積木文字、repeat、section、按鈕、設定說明、靜態選項、panel 名稱與套件描述。
官方 iframe panel 從 iframe URL 的 `lang` query 取得語言並使用自己的同版 catalog；
第三方 panel 不強制採用，但同樣會收到 query，方便日後自行支援。

修改 Pydantic 模型後，依既有流程重新匯出 `packages/shared-schema/manifest.schema.json`
並重新產生 Editor TypeScript 型別，不直接手改產物。

## 4. 後端與歷史錯誤

所有第一方、會到達 UI 的錯誤改為「穩定代碼＋參數＋回退文字」，避免歷史紀錄在
寫入當下被永久綁成某一語言：

```json
{
  "code": "project.not_found",
  "params": { "projectId": "prj_123" },
  "message": "找不到專案 prj_123",
  "hintCode": "project.save_before_run",
  "hintParams": {},
  "hint": "先存檔再執行",
  "blockId": null,
  "path": null,
  "action": null
}
```

- 集中定義第一方 error code 與必要 params，讓 `HTTPException`、`ValidationError`、
  `BlockyardError` 共用同一種 payload；既有 `message`／`hint` 保留作為舊客戶端與
  未知 code 的回退，既有 `blockId`、`path`、`action` 不改語意。
- **後端不維護第二份文案表。** `message`／`hint` 永遠是繁中回退，**所有**顯示用
  的翻譯都在前端拿到 `code`／`params` 之後才做——HTTP、WebSocket 與歷史紀錄走
  同一條路。理由：既然歷史事件已經決定「顯示時才翻譯」，HTTP 沒有理由例外；
  兩邊各養一份雙語表的結果是兩份會慢慢漂移的文案，而測試只顧得到前端那一份。
  第一版因此不做 `Accept-Language` 協商（§8）。
- WebSocket 即時事件與 SQLite 歷史事件保存語言中立的 `code`／`params`，前端在
  `RunPanel`、`HistoryPanel` 與積木警告實際顯示時翻譯。舊歷史只有 `message` 時照
  原文顯示；切換語言後，新格式的舊 Run 可以立刻以新語言查看，無須遷移資料庫。
- `try_catch` 暴露的錯誤物件保留 `message` 以維持既有流程相容，並增加
  `code`／`params`。畫面顯示採 catalog；流程自行讀取或輸出的 `message` 視為執行
  資料，不偷偷改寫。第三方／外部 SDK 例外只包一個安全的第一方外層 code，原始
  細節作 fallback，不嘗試機器翻譯。
- 盤點並轉換所有會送到前端的第一方 API route、IR／manifest validator、內建積木、
  trigger、run manager 與 key/import/bundle/file 流程。純開發者 traceback、CLI 與
  server log 不在 UI 語系範圍。

## 5. 右上角互動與版面

- 從執行／監聽 `.actions` 移除原本的 History icon 與其分隔線；`HistoryPanel` 本體
  保留。`PluginActions` 若存在排在固定入口之前，最右側順序永遠是 `KeysEntry`、
  `SettingsEntry`。
- Settings gear 在載入中與錯誤畫面仍可使用，讓使用者隨時切換語言；「歷史紀錄」
  保持原本的可用條件，在專案尚未 ready 時 disabled，「語言」始終可用。
- 設定選單使用 `role="menu"`，gear 帶 `aria-haspopup`、`aria-expanded` 與
  `aria-controls`。選單靠 gear 右下方對齊並限制在 viewport 內；點外面、Esc、視窗
  blur／resize／scroll 都關閉，關閉後焦點回 gear。支援上下鍵、Home／End 與
  Enter／Space 啟用項目。
- 語言 modal 使用既有 `.modal-backdrop`／`.modal`、focus trap 與 Esc 規則。
  兩個大列以原生名稱顯示，目前語言有 check 與 `aria-current`；點另一語言時先
  `writePref('locale', locale)`，再 `location.reload()`。背景點擊可關閉，關閉後焦點
  回 gear。
- 選單、modal、金鑰與歷史的名稱本身也走 catalog：繁中顯示「歷史紀錄／語言」，
  英文顯示「Run history／Language」。

## 6. 實作順序

1. 建立 locale 偏好、catalog、格式化函式與測試，先替應用殼、ProjectsPage 和
   Editor 第一方字串接上 `t()`。
2. 完成設定選單、語言 modal、History 入口搬移與鍵盤／焦點行為。
3. 後端加 `defaultLocale` 與 `locales/` 載入（含 §3.4 的降級規則）、schema 與
   generated TS types、前端 `localizeManifest`。
4. 加 `blockyard i18n extract` / `check`，用它產出並補完所有內建及官方積木／panel
   的 `locales/en.yaml`。
5. 將第一方錯誤正規化成 code/params，WebSocket／HTTP／歷史畫面統一改為顯示時翻譯。
6. 全產品逐頁盤點殘留的使用者可見硬編碼文字，完成雙語端到端驗收。

## 7. 測試與驗收

### 自動測試

- locale 偏好：缺值、合法值、損壞值、storage 丟例外；預設皆回 `zh-TW`，寫入後
  可跨 route 讀回，並正確設定 `<html lang>`。
- catalog：繁中與英文 key 集合完全一致；參數插值、複數、日期／時間在兩種 locale
  輸出正確；正式 fallback 不會把缺 key 畫成空字串。
- manifest 與 locales：沒有 `locales/` 的舊包照常載入；`defaultLocale` 回退鏈
  （requested → default → 原文）逐欄正確；部分翻譯逐欄回退；完整英文翻譯會改變
  分類、積木、參數、選項、按鈕、設定與 panel 名稱，但不改 opcode、arg key、IR 或
  Blockly block type。
- 翻譯降級：id 不存在或 placeholder 不一致的 `locales/en.yaml`，**載入成功**、
  該語言被忽略、字退回原文並留下一筆警告；同一份包在 `blockyard i18n check`
  下硬失敗。
- `i18n extract`：產出的 key 集合等於 manifest 所有可翻欄位；重跑保留既有翻譯、
  補上新 key、標出原文已改動的項目。
- Blockly：兩種 locale 各註冊一次真實 builtins，工具箱與 context menu 使用相符
  語言；同一份專案在兩種語言下 round-trip 後 IR 完全相等。
- 設定 UI（Vitest + jsdom）：右上角順序、gear 展開／關閉、外點與 Esc、完整鍵盤
  導覽、disabled history、開啟既有 HistoryPanel、語言 modal、目前語言標示、偏好
  寫入及只在語言真的改變時 reload。
- errors：後端回應永遠帶 `code`／`params` 且 `message` 為繁中回退；前端在兩種
  locale 下顯示正確、未知／舊 code 回退 `message`；即時與歷史 `block.error` 翻譯、
  params 不遺失、`blockId/path/action` 維持；舊 SQLite event 不需 migration 也能讀。
- 後端現有 unit／contract／conformance、Editor `npm run check` 與 production build
  全數通過；schema 與 generated types 的 `--check` 不得有差異。

### 手動驗收

1. 新瀏覽器第一次開啟仍是繁中；進 Editor 後右上角最後兩顆為金鑰、設定。
2. 設定選單開啟後可進既有歷史紀錄；歷史的清單、分頁、重新整理與關閉皆維持原功能。
3. 選 `English` 後目前頁面重載，專案列表、Editor、modal、Blockly、內建與官方積木、
   官方 panel 及第一方錯誤均為英文；畫布內容、未存狀態與專案資料不受語言切換影響。
4. 重開瀏覽器與切換專案仍為英文；選「中文（繁體）」後同樣立即重載並完整恢復繁中。
5. 安裝沒有 `locales/` 的舊第三方包仍成功，該包文字保持原文；其他第一方 UI 仍為
   英文。裝一個 `locales/en.yaml` 故意寫壞的包：安裝成功、該包退回原文、其餘正常。
6. 切換語言不改 manifest、project JSON、Run 結果或執行語意。

## 8. 相容性與非目標

- 不修改專案 IR，不新增資料庫 migration，不把 locale 寫進 project metadata。
- 不自動翻譯使用者內容、log、外部 API 回應、第三方 manifest／panel／插件文字。
- 第一版後端不做 `Accept-Language` 語言協商：翻譯只發生在前端顯示時（§4）。
  真的出現沒有前端的消費者（CLI、直接打 API）需要英文時再另案處理。
- 不在第一版加入更多語言、瀏覽器語言自動偵測、帳號雲端同步或不重載熱切換。
- manifest 原文字串與 error `message` 暫時保留；待第三方生態與舊客戶端有明確升版
  策略後，才能另案評估是否收緊為必須提供結構化翻譯。

## 9. 尚未決定

英文介面下一個只有中文的第三方包，工具箱裡會出現一段中文積木——使用者分不出
那是「作者沒翻」還是「壞了」。要不要在擴充卡片或安裝審閱畫面說一聲「此積木包
未提供 English」，還沒決定，不在上面的範圍內。
