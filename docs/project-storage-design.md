# 專案的一生

> 一份專案存在哪、怎麼帶出門、到了別人手上怎麼跑起來。
> 積木包自己的一生在 [`extension-design.md`](extension-design.md)；
> 積木語意與 IR 在 [`design.md`](design.md)。
>
> 狀態：**施工順序那六項全部做完了**（2026-09-05）。這份文件從設計稿變成
> 「它為什麼長這樣」的紀錄——每一節的規則都還在，只是主詞從「要做」變成
> 「做了」。**實作與設計不一樣的地方寫在最後一節**，那幾處都是寫下去才問得
> 出來的問題。

## 0. 現在是什麼樣子

後端**已經是多專案的**：`projects` 表有 `(owner_id, id)` 主鍵，`/api/projects`
的列表、讀、寫、刪四條路都在，`owner_id` 從 P0 就留著（§16 Q1）。

前端原本**寫死一個**：`App.tsx` 的 `const PROJECT_ID = 'prj_local'`。

現在那一行讀的是 `project/current.ts`——一個 localStorage 裡的 opaque id。多的
四條路是 `POST /api/projects`（開一個新 id）、`PATCH`（只改名字）、
`/export`＋`/import`（帶出門與收回來）、以及 `/api/files/save-dialog`（那顆
「瀏覽…」）。

## 1. 三個問題被綁成一個

「專案要不要包 extension」聽起來是一題，實際上是三題，而它們的答案不一樣：

| | 問題 | 答案 |
|---|---|---|
| **存哪** | 一份**活著的**專案在這台機器上是什麼 | SQLite 的一列 + 一個穩定的 id（現況不動） |
| **帶什麼出門** | 一份**寄給別人的**專案是什麼 | 一個 bundle，**裡面有積木包的原始碼** |
| **身分** | 「這個專案」在別的地方（keyring、trigger、執行歷史）怎麼被指到 | **一個 id，永遠不是它的位置** |

第二題就是你說的「一定要包 extension 進去啊，不然怎麼跑」——**同意，而且沒有
別的辦法**。但它不等於「積木包裝在專案資料夾裡」。

## 2. 決議：儲存是參照，運輸是打包

**活著的專案只記 id**（IR 的 `extensions` 已經是這個形狀，§13.3），程式碼住在
per-machine 的那個 store（`~/.blockyard/extensions/`）。**匯出時才把用到的那幾個
包的原始碼複製進 bundle。**

這不是折衷，是兩件不同的東西：

* **store 是共用的。** 五個專案都用 `discord`，磁碟上一份、venv 一份
  （實測 `discord` 13M、`openai` 31M——不是天文數字，但它會隨專案數線性長，
  而那是白花的）。
* **bundle 是自足的。** 它要在一台什麼都沒有的機器上展得開。

先例是同一個形狀：git repo 記依賴的名字、release tarball 帶著它們；uv 與 pnpm
用一個共用 store 加硬連結；Docker 的 image 與 Dockerfile。**沒有一個系統把
「我電腦上的安裝」與「我寄出去的那一份」做成同一個東西**，因為它們的最佳形狀
剛好相反：前者要去重，後者要自足。

它同時保住 `extension-design.md` §1 的三層帳：**專案層一個動詞都沒有**——它是
從畫布上的積木算出來的事實。匯出是讀那個事實，不是編輯它。

## 3. 專案的身分是一個 id，不是它的位置

**這是這份文件裡唯一有時效的決定**，其餘都可以之後再做。

已經有四樣東西拿專案當 key：

| 誰 | key |
|---|---|
| 執行歷史（§6.3） | `project_id` |
| trigger 的 active 狀態（§9.2） | `project_id` |
| webhook 簽章密鑰（§16 Q22） | keyring 的 `webhook:{專案}` + blockId |
| 每個專案自己的金鑰（§16 Q23，還沒做） | keyring 的 `{專案} + ext_id.key` |

**後兩個住在 OS 鑰匙圈裡，而鑰匙圈不會跟著資料夾搬家。** 如果專案的身分是它的
路徑，那麼「把資料夾拖到別的地方」就等於把使用者的 webhook 密鑰與金鑰全部弄丟
——而症狀是「我什麼都沒改，它說沒設定」。

這不是假想。**這個專案今天剛被同一件事咬過**：改名 Blockyard 那一次把 keyring
的服務名從 `blocky` 改成 `blockyard`，金鑰一把都沒掉，但畫面上全部變成「未設
定」，而沒有任何東西說得出為什麼。改一個字串就是搬一次使用者資料——這條規則要
寫下來，是因為它已經證明過自己。

所以：**id 是 opaque 的、產生一次就不變、跟位置無關。** 專案改名、搬家、匯出再
匯入回來都不動它。以後真要變成「一個資料夾就是一個專案」（Q25 的檔案那條線會
把它推過來），那也只是多一個 `path` 欄位指向它——上面四張表一個字都不用改。

## 4. 專案面板：多專案會弄壞的那一件事

面板本身很小：列表、新建、切換、改名、刪除。後端四條路都在。

> **它後來不是一個面板，是一頁。** 網址上有三個地方：`/` 導到上次那一份、
> `/projects` 是主選單、`/p/prj_ab12cd34` 是編輯器（`project/routes.ts`）。
> 理由見這一節最後那段「為什麼搬到網址上」。

**但它會弄壞工具箱那份名單。**

`extensionsStore` 的 `enabled` 存在 localStorage，是**整台機器一份**；載入專案時
`initEnabled` 做的是**聯集**（偏好 ∪ 這個專案用到的，D31）。單專案時那是對的。
多專案時它變成一個只進不出的桶子：

```
打開 A（用 discord）→ 名單 = {discord}
打開 B（用 openai） → 名單 = {discord, openai}
回到 A             → 名單還是 {discord, openai}
```

於是分類欄上永遠留著你在**別的專案**裡用過的包，而 D31 擋的正是這件事（60px 寬
的一直排，每一格都不會自己消失）。

**修法：`enabled` 從「一份」變成「每個專案一份」**，localStorage 的 key 帶上
專案 id。聯集規則不動——它在一個專案內仍然是對的。這不違反 §16 Q15（偏好不進
`project.json`）：它仍然存在瀏覽器裡，只是多一個維度。**「同一份專案在不同人手
上長得一樣」那條線沒有動。**

**做了。** `extensionsStore.ts` 的 `enabledPrefKey()`，回歸測試在
`enabledPerProject.test.ts`——那三題測的就是上面那個桶子。多專案之前那份
「整台機器一份」的名單**只有 `prj_local` 接得到**：讓每個新專案都繼承它，等於
把同一個症狀從跨專案搬到新專案身上。

> 這件事要跟專案面板同一步做。分開做的話，中間那段時間的症狀是「工具箱上多了
> 我沒加過的東西」，而那是最難連回原因的一種。

### 為什麼「現在開著哪一份」搬到網址上

第一版是一個疊在畫布上的面板，而「打開的是哪一份」住在 localStorage。它會動，
但有兩件事說不通：

* **專案的身分本來就是一個 opaque id**（§3），而網址是那個身分最自然的容器。
  住在 localStorage 的身分是一個**看不見、按不到、分享不了**的東西——上一頁、
  書籤、兩個分頁各開一份，三件事一件都做不到。
* **返回沒有一個穩定的目標。** 面板疊在畫布上，所以返回的意思是「回到我剛剛那張
  畫布」——而在剛刪掉一份、或正要切走的時候，那張畫布根本不存在。

所以列表變成家（`/projects`，**它沒有返回**），編輯器是走進去的一個地方
（`/p/<id>`，左上角那顆按鈕是「← 專案」，按下去會先替你存檔）。

**`/` 落在上次那一份，不是主選單。** 每天回來繼續弄同一個專案的人，落在選單上
就是每次多一次點擊，而那是這個工具九成的使用情境（VS Code 開上次的資料夾、
Notion 開上次那一頁，走的都是這條）。落在列表是給真的在很多檔案之間跳的人用的。

**切換仍然是整頁載入**——它本來就是（見下面那節），差別只在於它現在是一次真的
導覽，所以上一頁按得回來。

**擴充功能面板留著當疊層**，它不是一個地方，是一個蓋在畫布上的工具：它的返回
回到的是那張**還在的**畫布。兩顆返回不會同時出現在畫面上，因為主選單那一頁根本
沒有那顆。

## 5. 匯出：bundle 長什麼樣

```
我的專案.blockyard          （就是一個 .zip）
  bundle.json               ← 格式版本、匯出時間、帶了哪幾個包、每個包的 digest
  project.json              ← IR 原文，一個欄位不多一個不少
  extensions/
    greet/
      manifest.yaml
      main.py
      ...
```

**不帶 venv**（同意你的判斷）：裡面的路徑是絕對的，換一台機器就錯——`install.py`
的 `PACK_SKIP_DIRS` 早就在解壓那一步丟掉 `.venv` 了，同一條規則。依賴在收的那一
端從 `requirements` 重建（§7.6），見第 8 節。

**不帶收據**（`.blockyard-source.json`）。理由與「一個包不能自己說自己從哪來」
一模一樣，只是主詞換成一份 bundle：**別人的專案檔不能告訴我的機器某個包是官方
的。** 收的那一端自己開一張新的（`origin: "bundle"`）。

**`digest` 帶著走**（`extension-design.md` §2 的收據已經有這一格）。它在收的那
一端回答一個具體問題：「我手上這個 `http`，跟這份 bundle 裡的是不是同一個」。
見第 7 節。

### 匯出面板

你畫的三件事，兩件照做、一件我建議改：

```
┌─ 匯出專案 ─────────────────────────────┐
│                                        │
│  存到   ~/work/repos/bots/         〔瀏覽…〕│
│                                        │
│  ☐ 一併匯出金鑰（另存成 我的專案.env）      │
│      discord.bot_token   ····Y-Y4      │
│      openai.api_key      ····i84A      │
│                                        │
│  這份 bundle 會帶 2 個積木包的原始碼        │
│                                        │
│                        〔取消〕〔匯出〕   │
└────────────────────────────────────────┘
```

三格都照做。「瀏覽…」怎麼給出一個真的路徑是 §10——**它是這份設計裡唯一一個
需要新開後端能力的東西**，所以單獨一節。

## 6. 金鑰：那個勾選框撞到 D28

D28 白紙黑字：

> Key 不能存進 `project.json` **或跟專案檔同一個資料夾**——分享專案會變成分享
> 明文金鑰

而 D28 的補充還寫著「**匯出成 `.env` 仍然不做**」。所以「勾一下就把金鑰打包進
去」正面撞上它，而那條線的理由沒有過期。

**但需求是真的**：換一台機器、把專案交給同事，沒有金鑰它跑不起來。

### 真正危險的不是「刻意匯出」，是「看起來一樣」

一份帶金鑰的 bundle 與一份不帶的，如果是**同一個檔案**，那它就會被轉寄、被丟
上 GitHub、被貼進 Slack——而那一刻沒有人記得三天前勾過什麼。

**所以答案是兩個檔案，不是一個檔案裡的一個旗標：**

```
我的專案.blockyard        ← 永遠安全，這才是「專案」
我的專案.env              ← 勾了才有。它自己看起來就像一份金鑰
```

* 轉寄「那個專案」自然只會帶到第一個。
* 要搬機器的人拿兩個，收的那一端把第二個餵進**已經存在的** `.env` 匯入
  （D28 保留了整份匯入那條路），值進 keyring，檔案不留下。
* `.env` 這個副檔名本身就是一句警告——每個開發者都知道它不該進 git。

**定案。** D28 那條線（「金鑰不進專案檔」）因此**沒有被放寬，只是被說得更準**：
不是「金鑰不能離開這台機器」，是**「一份專案不能夾帶金鑰」**。兩個檔案讓後面
那句話仍然是真的，而前面那句話本來就不是 D28 說的。

### 勾選框旁邊要列出**這次會走出去哪幾把**

不是「要不要匯出 secret」一句話，是：

```
☐ 一併匯出金鑰（另存成 我的專案.env）
    discord.bot_token   ····Y-Y4
    openai.api_key      ····i84A
```

範圍是**這個專案用到的那幾個包宣告過的 secret**，不是整個鑰匙圈。末四碼那個
形狀 `/api/keys` 已經在給了（D28）。沒有這份清單，那個勾選框是在要求使用者對
一件他看不見的事負責。

## 7. 匯入：它就是「匯入 N 個包」

**收一份 bundle = 開一個新專案 + 走 N 次已經蓋好的那條安裝管線**
（`extension-design.md` §3）。不必發明新機制。

### 一個包一頁，加一顆說出自己在略過什麼的按鈕

**審閱畫面照舊、一個包一頁**（§12.1 的「完整顯示原始碼」一個字都不放寬），
但要有一條出口：

```
┌─ 這份專案帶了 3 個積木包 ──────────────┐
│  第 2 個，共 3 個                        │
│                                        │
│  greet · v0.1.0 · 由 alice 寫的          │
│  權限：無    依賴：無                     │
│  ⚠ main.py:14 用了網路，但沒有宣告 net    │
│                                        │
│  ── main.py ──────────────────────     │
│  …完整原始碼…                            │
│                                        │
│  〔略過其餘 2 份原始碼，直接安裝〕  〔安裝這個，下一個〕│
└────────────────────────────────────────┘
```

**那顆批次按鈕的字要說出它在略過什麼。** §12.1 那句話是「不可略過」，所以真的
要加一條略過的路，最起碼它得**把那個字說出來**——「全部通過」聽起來像是有人
通過了什麼，而實際發生的事是沒有人看。名字誠實比擋下來有用，因為擋不住的東西
擋了只會被繞過。

**位置在主要動作旁邊，不在標頭。** 一顆放在頁面最上方的略過鍵是使用者第一眼
看到的東西，於是它變成預設路徑，而審閱畫面就真的成了儀式。放在下面，至少他
捲過了第一個包的摘要。

### 唯一的例外：靜態掃描亮紅燈的那幾個不進批次

`codescan.py` 已經在算 `findings`，而且每一筆帶著 `declared`——**「這支程式碼
做了一件它沒有宣告的事」**。那正是一眼有價值的地方，也是這個掃描器存在的全部
理由。

所以：**有未宣告 finding 的包不被那顆批次鍵蓋掉**，它們留下來、列出名字，一個
一個各要一次確認。

這**不是**擋下來——按下去它照樣裝得進去，一個包多一次點擊。它守的是一件很小
但很具體的事：**一顆能把紅燈一起吞掉的批次鍵，會讓 `codescan.py` 從此不存在。**
而那個掃描器是這條路上唯一會主動說話的東西。

（沒有 finding 的包——絕大多數——完全不受影響，一鍵到底。）

### 次數本來就不多

| 狀況 | 怎麼辦 |
|---|---|
| bundle 裡的包**已經裝了，而且 digest 一樣** | **完全不出現**。沒有任何新的程式碼要進來 |
| 裝過了、但 **digest 不一樣** | **預設跳過，並且說出來**：「這份專案帶了一個不一樣的 `http`」。覆蓋是更新（§16 Q24、`extension-design.md` §4），不能靠匯入偷渡 |
| 沒裝過的包 | 進審閱，一個一頁 |

第一列讓最常見的路完全沒有摩擦：**「三分鐘做一個 Discord bot」那份 demo 帶的
都是官方包，收的人一個審閱畫面都不會看到。** 審閱只在真的有新程式碼要進到這台
機器上時出現——而那時候它本來就該出現。

### 收下來的包，收據寫 `origin: "bundle"`

`label` 是那份 bundle 的檔名，所以卡片上那一行會是
「2026-09-04 從 我的專案.blockyard 裝的」。這是 `origin` 字彙表的第五個字
（`extension-design.md` §8 說要封頂）——它進得來，因為它對那兩個讀者都給得出
不同的答案：卡片要說得出這個包是跟著誰進來的，而它跟 `official` 一樣是可以
移除的。

## 8. 依賴：進度條屬於匯入，不屬於首次載入

同意「不包 venv、在收的那一端裝」。但**位置我建議往前挪一步**。

`install.py` 現在的順序是**先建 venv 再搬進去**，因為 `ensure_interpreter()`
（`uv pip install`）是這條路上唯一真的會失敗的一步（網路、`uv` 沒裝、版本解不
開），而先搬後建的失敗會留下一個「裝在那裡、拉出來卻跑不動」的包。

同一個理由讓進度條該掛在**匯入**上而不是「首次載入專案」：

* 匯入時使用者正在「我在裝東西」的心情裡，等待與失敗都在預期內。
* 「打開專案」的心情是「我要開始工作了」，而那一刻跳出一條裝三分鐘的進度條、
  然後說 `uv` 沒裝——**那個失敗會被理解成「這個專案壞了」**，而不是「這台機器
  還缺東西」。

匯入做完，專案就是可以跑的。這也讓「打開專案」永遠是一個快動作。

**進度長什麼樣：一格一格，不是百分比。** 我們知道有幾個包、正在裝第幾個，但
不知道 `uv` 走到哪裡。一條從 33% 跳到 66% 的假進度條比一句
`正在安裝 discord 的依賴（3 之 2）` 更難讀——它承諾了一個我們給不出的精度。

## 9. 那顆「瀏覽…」：tkinter 的原生對話框

**這是這份設計裡唯一一個需要新開後端能力的東西**，所以規則要寫得比別處細。

### 先說結論

**用 tkinter 開一個真的系統對話框。** 我原本建議「不要路徑欄、走瀏覽器下載」，
理由是「瀏覽器給不了路徑，所以那格只能手打，而手打比對話框難用」——**那個理由
在有 tkinter 之後就不成立了**：它給的不是一格文字，是使用者每天在用的那個
「另存新檔」。

實測（2026-09-04，這台機器）：`backend/.venv` 的 Python 有 tkinter，Tk 9.0，
在一個乾淨的 subprocess 裡開 hidden root 正常結束。

### 但它會寫到磁碟上，所以要一條規則

**後端寫的位置只能來自它自己剛剛開的那個對話框，永遠不能來自 request body。**

這條線把 §16 Q25 標的那個安全面關在外面。差別具體到一句話：

| | 誰指定路徑 | 安全嗎 |
|---|---|---|
| `POST /api/…/export {"path": "/Users/x/.ssh/authorized_keys"}` | **網頁** | 不。那是一個任意寫入端點，而它從瀏覽器打得到 |
| 對話框回一個路徑 → 後端記在一個一次性 token 底下 → `POST {"token": …}` | **人** | 是。網頁從頭到尾沒有說出過任何路徑 |

所以形狀是兩步，而路徑**只以顯示字串的身分**經過瀏覽器：

```
POST /api/files/save-dialog   → { token, display: "~/work/bots/我的專案.blockyard" }
POST /api/projects/{id}/export { token, secrets: false }
```

token 一次性、有期限，用掉就作廢。**畫面上那一格路徑是唯讀的**——它是給人看的
回執，不是一個輸入框。

### 四條實作規則

1. **一定走 subprocess，不在 uvicorn 的行程裡開 Tk。** Tk 要求主執行緒，而請求
   處理跑在事件迴圈或執行緒池上——macOS 上那會怪掉或直接爆掉。開一支
   `sys.executable -c "…"`，它印出路徑就結束。順帶：一個卡住或崩掉的對話框
   因此帶不走後端。
2. **只在後端跟瀏覽器是同一台機器時給。** 對話框開在**後端**那台的螢幕上。今天
   那永遠是同一台（只綁 127.0.0.1，§12.1），但 `blockyard serve --host` 已經
   允許別的綁法。少了這條，症狀是**一個沒有人在看的螢幕上開了一個視窗，而那個
   HTTP 請求永遠不回來**。判準用「這個請求來自 loopback」，不是設定值。
3. **要有逾時，取消要回得乾淨。** 使用者按取消 = 空字串 = 這件事沒發生，不是
   錯誤。逾時之後那個 subprocess 要被殺掉。
4. **tkinter 不在就退回瀏覽器下載。** 某些 Linux 發行版要另外裝 `python3-tk`。
   偵測一次、記著，然後那顆「瀏覽…」不畫——匯出仍然成立，只是落到下載目錄。

### 一個會浪費半小時的細節

**原生對話框會開在瀏覽器視窗後面。** 使用者按了「瀏覽…」，畫面沒反應，因為
那個視窗在下面。macOS 上要在 subprocess 裡把它拉到最前面
（`root.attributes("-topmost", True)`，必要時 `osascript` 把行程 activate）。
這是「按了沒反應」這句 bug report 最常見的來源之一。

### 它是一條死路，而那沒關係

P4 的 Tauri 會換掉它（§16 Q25 就是這樣寫的）。**這不是問題，因為它是三十行。**
換過去的時候，上面那條 token 規則一個字都不用改——變的只是誰開那個對話框。

同一支東西順帶把 Q25 的另一半也解決了：**「選一個 200MB 的影片」** 用的是同一個
對話框，只是換成 `askopenfilename`。所以這三十行不是為匯出寫的，是為
`type: "path"` 先蓋了一半。

## 10. 沒答的

* **同名怎麼辦。** 匯入一份專案，而這台機器上已經有一個同名的——改名、覆蓋、
  還是並存？（id 是 opaque 的，所以技術上一定並存，問題只在畫面上怎麼說。）
* **`extensions` 是算出來的，那匯出要不要「多帶」？** IR 的 `extensions` 來自
  畫布上真的用到的積木。一個使用者加進工具箱、還沒拉出積木的包**不會**進
  bundle——正確，但收的人打開之後工具箱上就少那一格。要不要一起帶是一個取捨，
  傾向不帶（bundle 描述的是這份專案，不是我當時的桌面）。
* **bundle 要不要記「我從哪個 registry 拿的」**（§7 的登記處落地之後）。帶了
  就能一鍵更新而不是永遠停在寄出去的那一份；但那也是 `extension-design.md`
  §8 那條「一份專案檔可以叫別人的機器去下載並執行程式碼」的顧慮。**登記處做
  之前不必答。**
* **Q25 落地之後專案要不要真的變成一個資料夾。** 第 3 節那條規則讓這一題可以
  晚點答：id 不變，多一個 `path` 欄位就好。
* **`.env` 那個檔案要不要有一個對應的「匯入專案時順便問你要不要餵它」。**
  現在的答案是不要——兩個檔案的意義就在於它們是兩個動作。
* **批次審閱那顆鍵要不要記住選擇**（「這個來源以後都不用問我」）。傾向不做：
  那會讓 §12.1 從「每次都給你看」變成「第一次給你看」，而 bundle 的來源是人
  不是機構，記不住的東西記了只會過期。

## 施工順序（做完了）

判準與 `extension-design.md` 同一條：**哪一項之後會變貴**，不是哪一項比較急。

| # | 做什麼 | 為什麼排這裡 |
|---|---|---|
| ✅ 1 | **§3 那條規則寫下來**：專案的身分是 opaque id，跟位置無關 | **唯一有時效的一項**，而且它是一句話不是一段程式碼。今天的 keyring 事件就是它的證據 |
| ✅ 2 | **專案面板**（列表／新建／切換／改名／刪除）＋ **§4 的 `enabled` 改成每專案一份** | 後端四條路都在，缺的是面板。第二半必須同一步做，不然症狀是「工具箱上多了我沒加過的東西」 |
| ✅ 3 | **匯出**（bundle ＋ 瀏覽器下載，**先不做金鑰、先不做路徑**） | 自足的那一半先成立。沒有金鑰仍然是一份可以打開、看得懂、缺什麼說得出來的專案 |
| ✅ 3b | **原生對話框**（§9：subprocess、loopback、逾時、退回下載） | 拆出來是因為它是**唯一一項新開後端能力**的。3 不等它也成立（落到下載目錄），而它做完順帶蓋好 Q25 一半的 `type: "path"` |
| ✅ 4 | **匯入**（開新專案 ＋ 走安裝管線 ＋ 一個包一頁的審閱 ＋ digest 比對） | 匯出的雙胞胎。**要積木包那邊的第 3 步（收據）**，`digest` 就是從那裡來的 |
| ✅ 5 | **金鑰匯出／匯入**（第二個檔案 ＋ 那份清單） | 排最後**不是因為難**，是因為它是唯一一項會讓一份檔案變危險的。前面四項全部安全落地之後再加它 |

**§16 Q23（secret 分不分專案）在第 5 步之前答了：全部分專案。**

那份設計原本傾向 (b)——由積木包作者在 manifest 上宣告哪一把該分專案。改成
「全部分」的理由是**這一版還沒有第二個人在寫包**：(b) 要求包作者在他寫下
`secret` 的那一刻，替一個他看不到的使用者決定「你會不會有兩個專案接不同的
Discord」——而那個判斷他答不出來。全部分專案的答案永遠是對的，代價是**換一個
專案要重填一次**，而那個代價現在由使用者自己吸收（金鑰面板給得出完整明文，
D28 的 `/reveal`，複製過去就好）。

「從別的專案帶一把過來」是之後的事，而它加得進來：keyring 的 username 是
`{專案 id}:{ext_id}.{key}`，多一條「複製到另一個專案」不動任何既有的格式。

**P0b 存下來的那些沒有專案維度**，所以啟動時搬一次（`secret_store.migrate_legacy`）。
不搬的症狀就是 §3 那件事：金鑰一把都沒掉，但畫面上全部變成「未設定」。

## 實作與這份設計不一樣的地方

寫下去才問得出來的那幾個問題。

* **匯入時 id 沿用，撞號才換。** §3 說「匯出再匯入回來不動 id」，§10 說「技術上
  一定並存」——兩句話在同一份 bundle 上會打架。落點是：**bundle 裡那個 id 沒有
  人占用就沿用**（那讓 keyring 裡那幾把金鑰仍然指得到同一個專案），占用了才開一個
  新的。回應帶一個 `reusedId`，所以畫面說得出發生了哪一種。
* **刪掉專案 = 連它自己那幾把金鑰一起刪。** 這份設計沒寫，而不刪的結果是一堆
  永遠讀不到的明文躺在鑰匙圈裡（專案 id 是 opaque 的，沒有第二條路指得到它們）。
  刪除的確認對話框因此把這件事寫在上面——它不是副作用，是使用者按下去之前就
  被告知的事。
* **切換專案是整頁載入。** 編輯器的狀態散在 Blockly 的工作區與註冊表、執行中的
  WebSocket、監聽狀態、值氣泡的裝飾器、下拉的 60 秒快取裡。在原地換掉一個專案
  就得為上面每一樣東西回答一次「它該被清成什麼樣子」，而漏掉任何一個的症狀都是
  「這個畫面上有一半是上一個專案的東西」。整頁載入讓那份清單只有一項。
* **面板變成一頁，而網址說得出你在哪裡**（見 §4 那段）。`project/current.ts`
  因此換了主詞：**網址是身分，localStorage 只是「上次那一份」的記憶**。反過來
  的話，兩個分頁各開一份時，後開的會把先開的身分改掉——而先開的那個分頁下一次
  存檔就存到別人身上去了。
* **編輯器不准自己生一份專案出來。** `App` 原本是 `loaded ?? blankProject()`，
  而那在 P0b 是對的（id 寫死、第一次啟動本來就沒有專案）。多專案之後同一行的
  意思變成：打開一個死掉的網址 → 看到一張空白畫布 → **一存檔就把那份被刪掉的
  專案復活**，或者無中生有一個從來不存在的專案。而 `/` 導去的正是「上次那一份」
  ——一個記在 localStorage 裡、可能已經在別的分頁被刪掉的 id，所以這條路一點都
  不罕見。現在讀到 404 就忘掉那個記憶、回主選單，並且說出是哪一份不見了。
  開一份專案是一個明確的動作，網址只能打開已經存在的東西。
* **後端多一條 SPA fallback**（`_EditorFiles`）。`/projects` 與 `/p/<id>` 是真的
  路徑，而磁碟上沒有那幾個檔案——少了它，**打包後重新整理一次就白畫面**，而 dev
  是好的（Vite 自己有這條），所以那個 bug 只會在打包之後出現。`/api`、`/ws`、
  `/hooks` 底下的 404 不吃這條：回一份 HTML 會讓前端把首頁當成 JSON 去 parse。
* **匯出面板問的是 `GET /export-plan`（積木包 ＋ 金鑰一次給）**，不是前端自己
  數。使用者在面板上匯出的可能是**另一份**專案，而那份 IR 前端手上根本沒有。
* **那顆批次鍵在頁面底部，而它說得出自己在略過什麼**（「略過其餘 2 份原始碼，
  直接安裝」）。§7 說「位置在主要動作旁邊，不在標頭」，而審閱畫面的主要動作
  （安裝）在標頭上——落點是頁尾：使用者至少捲過了這一個包的摘要，而它不會是
  第一眼看到的東西。
* **右鍵上多一個「複製」**（`POST /api/projects/{id}/copy`）。§4 那五個動詞裡沒有
  它，而它加進來只花一條路由：**新的 id、同一份 IR ＋ 同一張預覽圖**，名字是
  「X 的副本」（撞名往下數，因為卡片上只有名字與時間，複製兩次的時間差看不出來）。
  **掛在專案 id 上的那四樣一個都不跟**：金鑰、執行紀錄、webhook 網址、trigger
  開著沒有。那不是省事，是 §3 與 Q23 的直接結果——副本是另一個專案，而一份使用者
  還沒打開過的專案不該已經在收 Discord 訊息了。前端另外把 `extensions.enabled`
  那份名單也複製過去（它住在 localStorage，後端看不到），少了它副本的工具箱會
  掉一半（D31 的聯集只剩「這份 IR 用到的」）。做完**停在列表上**：複製的意思常常
  是「先留一份再改」，而把使用者送進副本的畫布等於替他決定了他要動的是哪一份。
* **下拉也要帶專案**（`POST /api/extensions/{id}/dropdown/{source}?project=`）。
  `discord.channels` 得先用**這個專案的** bot token 連上去才問得出頻道；少了它，
  換到第二個專案之後下拉會是空的，而空白不會告訴任何人原因。
